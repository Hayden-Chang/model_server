# 任务估时条件识别

状态：实现与本机接口验证，尚未部署；与 iOS 草稿 PR #320 配套。

`POST /api/duration/profiles` 使用现有设备令牌和 AI 额度。请求只包含
`requestID` 及 `tasks[{id,title,note}]`；拒绝额外字段（包括计划与实际分钟数）、
重复 ID、超过 32 项、单标题超过 500 字符、备注超过 2000 字符或总文本超过 24000 字符。
App 在用户明确启用后，发送当前查看任务及最多 20 项已完成历史；时长比较留在本机。

账号服务先预留额度，用短期、请求正文绑定的内部凭证调用
`/internal/time-fragment/duration-profiles`。成功且 ID 集完全匹配才扣一次额度；
模型失败、缺项、重复、额外 ID 或非法条件返还预留额度。沿用已有模型网关及原始推理
留存策略，不新增客户端密钥或公网内部入口。识别本身不需要历史用时。

结果包含类型、工作量、准备情况、熟悉程度和完整任务/投入时段。当前支持日常用餐、
按成片分钟衡量的视频剪辑、按 UI 页面数量衡量的开发，其余保持未知。不从任务安排
时长反推复杂度，不把所有“开发功能”强行映射到页面数量。缺少执行条件时返回 null。
模型必须给出来自输入的原文证据；找不到对应原文的字段清为未知。原文匹配只是守卫，
不能证明模型语义正确，因此 App 必须支持修正，不能声称识别准确率已验证。
仅投入指定时间的任务保留 `timeBudget`，服务端将类别与比较条件清为未知；
即使模型返回了有原文依据的类别，也不能把投入时段当成完成一项交付物的耗时。

测试以模型替身验证 JSON 提取、未知条件、契约边界、设备鉴权、额度拒绝、返还、
内部签名和代理正文。尚无真实模型准确率评估、线上部署或 iOS 到线上模型的端到端证据。
