# 看房搭子容量与点数兼容上线

本变更仅准备兼容服务，不包含生产部署。客户端配套为 rent_room PR #105；iOS 购买与消费仍在本机处理，不使用此钱包。登录后的小程序新建房源必须联网确认扣点。

## 协议与迁移

| 请求 | 行为 |
| --- | --- |
| 无版本、v1、v2 | 保留原容量字段及免费额度协议，仅统计 capacity 订单 |
| `X-Rent-Room-Capacity-Version: 3` | 同时保留旧字段，增加 `credits:{version:1,migrated,remaining?}`；catalog 增加 `creditVersion:1` |
| `POST /credits/migrate {active}` | 微信 session 鉴权；每账号一次，冻结免费额度及原本机未归档房源数 |
| `POST /credits/operations {requestId,action}` | reserve/commit/cancel 均按账号和请求号幂等；数据库写事务防止双设备透支 |

路径前缀均为 `/api/rent-room`。v3 下单前必须迁移；旧版下单继续记 capacity，新版下单记 credits。同一请求号跨版本重试维持初次下单语义。现有订单通过新增列默认归类 capacity，保留原商品 ID、价格快照、支付验证与退款处理。

初次余额为 `max(0, 免费容量 + 已确认旧购买额度 - 本机未归档房源数)`；历史超额先截断为零，不带入欠账。迁移后由已确认订单总点数减去冻结的旧占用和新建预留/消费计算余额；旧订单迟到支付仅增加一次，退款扣除原发放。配置免费额度变更不会给已迁移账号重复发放。

后端不存房源内容，也无法验证本机房源数量。首次成功升级设备提供迁移基数，第二台设备不会重新按自己的房源数迁移。多台旧设备记录不同、旧版继续创建、清除数据后才首次升级时，后端无法还原完整历史占用；不宣称所有旧版占用都与新钱包实时同步。旧设备维持原容量是本过渡策略的兼容承诺；新购买点数不反向扩充旧设备容量。新用户指使用新版客户端的用户，旧客户端新注册仍按兼容容量协议使用。

## 新建事务

客户端先持久化请求号，再 reserve，原子保存房源后 commit。保存失败 cancel；超时取消会写终态，即使晚到 reserve 也不能再扣点。已 committed 的 cancel 返回 committed，不返还点数。导入、归档恢复和删除不调用扣点接口。

预留不自动超时退款：房源可能已经成功保存，只是回包丢失。客户端重启/下次创建会用原请求号收尾。若清除本机数据导致未完成的请求日志丢失，预留会保留；需人工核对，不能按时间直接释放。服务仅存操作 ID、状态与时间，不接收房源名称、备注或影像。账本应和订单数据库一同备份。

## 发布顺序与回滚

1. 备份现有 SQLite（含 WAL 的一致快照），先合入并部署兼容后端；不批量迁移用户。
2. 在受控测试账号核对旧版 session/entitlements/下单仍为容量；v3 迁移、重复请求、退款和并发扣点通过。此 PR 的 FakeWeChat 测试不是生产支付验收。
3. 后端稳定后再发布新版小程序。第一次新版登录静默迁移；iOS 可独立按本机方案发布。
4. 观察 v3 迁移失败、操作冲突/不足、401、预留积压、支付核对与退款；暂停新购买可用已有 payments 开关，迁移/已有余额扣点仍可用。
5. 出现问题暂停客户端放量并保留兼容后端。存在 credits 订单后**不能回滚到不识别 entitlement_kind 的旧二进制**，旧代码会把点数订单误计为容量。回滚版本必须保留分类查询和钱包表，不能删表或把所有账号重新迁移。

代码合并、部署、小程序体验版、提审、正式发布各自独立。本次未执行这些生产动作。
